# 架构说明

## 一、分层

```
┌──────────────────────────────────────────────────────┐
│ ① 入口    web/（Chat）  agent/main.py（CLI）           │
├──────────────────────────────────────────────────────┤
│ ② 能力    skills/  query · selftest · trend · router  │
├──────────────────────────────────────────────────────┤
│ ③ 上下文  context/ assembler · graph_scene · timeline │
│           Task ↔ Change ↔ Graph ↔ Scene ↔ 历史        │
├──────────────────────────────────────────────────────┤
│ ④ 编排    agent/  planner · executor · judge · failure│
├──────────────────────────────────────────────────────┤
│ ⑤ 工具    tools/  r2 · forcebot · diff · llm          │
├──────────────────────────────────────────────────────┤
│ ⑥ 数据    store/  SQLite：场景/图/变更/任务/快照/报告  │
├──────────────────────────────────────────────────────┤
│ ⑦ 观测    observe/ tracer（本地） + tracing（LangSmith，可关） │
└──────────────────────────────────────────────────────┘
```

**可选路径**：`run` 链路有手写版（`skills/run.py`）和 LangGraph 版（`skills/run_graph.py`），
装没装 langgraph 自动切换，执行逻辑（`run.execute`）只有一份。见 D12。

**依赖方向**：`skills → context → store`，`agent → tools`。
**硬约束**：Skill 不允许直接查库，必须走 `context/assembler`——否则三个 Skill 会各写一套聚合逻辑，口径必然分叉。

## 二、三条数据流

**① 查询（只读）**

```
任务 id → assembler 装配上下文（变更 / 快照 / 历史 / 对照图）
        → timeline 算分布
        → DiD 算净影响
        → 结论卡（含可比性提示）
```

**② 自测（会触发任务）**

```
commit → 变更 → 图 → 场景（共享图自动扩容）
       → 预检（只挡确定性错误）
       → 计划确认 → 执行（trace）→ 判读
```

**③ 趋势（批量）**

```
场景 + 时间窗 → 任务序列 → 快照一致性校验
             → 前后分布对比 + DiD（对照场景）
             → 归因 → 必须指向一个动作
```

## 三、通用 Agent 分层 vs 本项目

业界 Agent 项目的常见分层（10 个能力域）与本项目的取舍：

| # | 通用能力域 | 本项目 | 说明 |
|---|---|---|---|
| 1 | 接口层 | ✅ `web/` + CLI | Chat 是探索入口，不是门禁（D4） |
| 2 | 编排层 | ✅ `agent/` | 规则优先（D1） |
| 3 | 角色 / Prompt | ⚠️ 单 Agent | 只有“质量编排”一个角色，拆多 Agent 是过度设计 |
| 4 | 工具层 | ✅ `tools/` | Mock 与真实同签名（D5） |
| 5 | **记忆** | ❌ **刻意不做** | 见下 |
| 6 | **知识 / RAG** | ❌ **不需要** | 判定依据来自阈值规则，不来自文档检索 |
| 7 | 护栏 | ✅ `failure.py` + `judge.py` | 失败分级（D3）、判读边界（D6） |
| 8 | 观测 | ✅ `observe/` | 从第一天就要有 trace |
| 9 | **评测** | 🚧 `evals/` | 刚起步，见 `evals/README` |
| 10 | 配置 / 测试 | ✅ `data/` + `tests/` | 17 个单测 |

### 三处刻意的省略

**① 不做记忆（memory）**

一般 Agent 的记忆分两种：

- **短期上下文**：多轮对话状态 —— 本项目的交互是「一问一答一任务」，任务状态落在 `task` 表里，不依赖对话上下文
- **长期记忆**：历史经验向量库 —— 本项目的“历史”是结构化的任务序列，用 SQL 查比用向量检索更准

> **什么时候要补**：当需要「上次类似问题是怎么解决的」这种模糊匹配时，才值得上向量记忆。

**② 不做知识库 / RAG**

判定依据是**阈值规则**（D6、D7），不是文档。把规则放进向量库只会让结论变得不可复现。

> **什么时候要补**：当规则数量超过几百条、且存在大量“例外情况说明”时才需要考虑。

**③ 不做多租户 / 计费 / SLA**

这是**内部质量工具**，不是对外 SaaS。多租户带来的隔离成本，换不来收益。

> **判断标准**：会不会有外部客户？不会，就不做。

### 反过来，这三样必须有

| 能力 | 为什么不能省 |
|---|---|
| **权限与审计** | 会有人的结论被问责 → 必须能查「谁批的」 |
| **可观测** | 长链路 + 异步任务 → 出问题要能定位到哪一步 |
| **幂等** | 重复触发不能重复跑，否则资源翻倍且出两个矛盾结论 |

## 四、工具接口

所有工具实现 `Tool.run(params) -> ToolResult`：

| 工具 | 输入 | 输出 |
|---|---|---|
| r2 | scene | status, record_success |
| forcebot | scene, qps | avg, p99, cpu |
| diff | scene, fields, ordered | diff_rate, top100_consistent |

Mock 与真实实现同签名，切换只改装配处（`web/server.py` 或 `agent/main.py`）。

## 五、数据模型

```
Change ──1:N──> Graph ──1:N──> Scene
                   │              │
                   └──────┬───────┘
                          ▼
                        Task
                     ├─ Snapshot（场景快照）
                     └─ Report（报告）
```

`scene_graph` 是 N:1（一个场景只属于一张图，一张图可被多个场景复用）——**共享图识别**靠它。
