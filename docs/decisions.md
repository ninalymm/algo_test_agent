## D1 规则优先，模型兜底

- **状态**：已采纳
- **日期**：2026-11-10
- **影响范围**：`agent/planner.py`、`agent/judge.py`

| 环节 | 用什么 | 理由 |
|---|---|---|
| 变更 → 场景 | 规则表 + LLM 兜底 | 80% 可枚举；未知变更回退全量 |
| 参数选择 | 规则 | 参数错 → 结论错 |
| 执行顺序 | 确定性 DAG | 顺序错 → 事故 |
| 结果判读 | 规则阈值 | 必须确定 |
| 归因解释 | LLM 辅助 | 仅作建议，不进结论 |
| 是否放行 | 规则 + 人 | 绝不由模型放行 |

**后果**

- 好的：结论可回归、可单测覆盖
- 坏的：新变更类型首次出现需人工补映射表；规则表会随业务增长膨胀

**何时重新评估**：未知变更占比 > 20%（规则表跟不上业务）；LLM 场景推荐离线准确率 > 95%

## D2 执行与判读分离

- **状态**：已采纳
- **日期**：2026-11-10
- **影响范围**：`agent/executor.py`、`agent/judge.py`

**决定**：执行层只返回数据，不做任何判定；判读层只看数据，不碰执行。

**理由**：判读逻辑可以脱离平台单测——换真实平台时，判读部分一行不用改。

**后果**

- 好的：执行与判读可独立演进、独立测试
- 坏的：多一层数据契约，改了执行返回结构要同步改判读

**何时重新评估**：判读需要依赖执行过程的状态（而非结果）时，这层分离会变别扭

## D3 失败分级处置

- **状态**：已采纳
- **日期**：2026-11-10
- **影响范围**：`agent/executor.py` 的失败处理、`agent/judge.py` 的结论生成

### 背景

压测或 diff 任务失败时，有三种可能的处置：重做、跳过、交人。

- 一律重做 → 浪费时间，且重做后数据可比性下降（跨轮次环境已变）
- 一律跳过 → 等于取消门禁
- 一律交人 → 会产生**审批疲劳**：人一天审 20 次，开始不看就点通过，比直接跳过更危险

而失败本身不是同质的：有的能自己恢复，有的已经给出了明确答案，有的才是真的不知道。

### 决策驱动

- 漏测不可逆，时间可恢复
- 处置动作应由**失败类型**决定，而不是由「这次赶不赶时间」决定
- 任何处置都要留痕，能回答「这次为什么放行」

### 候选方案

| 方案 | 优点 | 缺点 |
|---|---|---|
| A. 统一重做 | 最保守 | 慢；重复失败概率高；跨轮次数据不可比 |
| B. 统一跳过 | 最快 | 等于取消门禁，漏测风险不可控 |
| C. 统一交人 | 灵活，人能看上下文 | 高频审批必然形式化，门禁名义存在、实际失效 |
| **D. 按失败类型分级** | 把人的注意力留给真正不确定的情况 | 分级规则需维护，分类错了会误判 |

### 决定

选 **D**，分三级：

| 失败类型 | 是否可判定 | 处置 |
|---|---|---|
| 录制未就绪、瞬时超时 | 可自愈 | 自动重试 ≤ 2 次；仍失败转人工 |
| diff 超阈值、性能不达标 | 可判定 | 直接判「不通过」，**不进人工** |
| 任务执行报错、结果缺失 | 不可判定 | 人工介入 |

### 理由

三类失败的**信息量不同**：

- 前两类已经给出了答案——要么能修好，要么已经明确不合格；
- 只有第三类是真的「不知道」，才需要人补判断。

把已经知道答案的事交给人，只会稀释人对真正未知问题的注意力。
**门禁的价值不是「每次都有人看」，是「每次异常都有人负责」。**

### 后果

**好的**

- 常规失败自动消化，人只处理真正不确定的情况
- 每一次放行都有明确的责任人和理由，可回溯
- 自愈过程留痕，能统计「哪类失败最常发生」

**坏的**

- 分级规则本身需要维护，新失败类型出现时要补分类
- 分类判错会导致该自愈的进了人工，或该人工的被自动放行
- 自动重试会延长单次验证时长（最坏情况 +2 轮）

### 何时重新评估

- **人工介入率 > 20%** → 说明分级太粗，需要细化失败类型
- **自愈后二次失败率 > 50%** → 说明重试策略无效，应改为直接判失败
- **出现一次「该人工却被自动放行」的事故** → 分级规则需要整体重审

## D4 Agent 不是门禁

- **状态**：已采纳
- **日期**：2026-11-10
- **影响范围**：整体架构

**决定**：Agent 只提供执行能力，门禁必须由发布流程强制触发（webhook），而不是靠人想起来调用 Agent。

**理由**：Chat 入口降低门槛，但**解决不了「必须跑」**。靠自觉触发的检查，迟早会退化成「想起来才跑」。

**后果**

- 好的：门禁的强制性由发布系统保证，不依赖 Agent 的易用性
- 坏的：需要同时维护 CLI/Chat 与 webhook 两个入口（但共用同一套执行引擎）

**何时重新评估**：当发布系统本身能强制调用 Agent 时，Chat 入口可以只保留「探索」用途
