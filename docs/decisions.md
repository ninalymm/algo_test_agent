## D1 规则优先，模型兜底

- **状态**：已采纳
- **日期**：2026-11-10
- **影响范围**：`agent/planner.py`（场景选择）、`agent/judge.py`（结论解释）

### 背景

编排层要替人做三类判断：跑哪些场景、用哪档参数、结果怎么解释。这些判断过去由人凭经验做，现在要写进代码。

难点在于：业务里已经沉淀了大量**明确规则**（哪类变更影响哪些场景、阈值多少），但也有**没见过的新变更**。代码必须回答一个问题——规则和模型，谁说了算。

### 决策驱动

- 漏跑场景 → 漏测 → 不可逆；多跑场景 → 只是浪费时间
- 结论必须可回归：同样的输入，今天和一周后要得出同样的结果
- 规则是业务已经认可的事实，不能被模型"重新理解"一遍

### 候选方案

| 方案 | 优点 | 缺点 |
|---|---|---|
| A. 全规则 | 可预测、可单测、可回溯 | 遇到未见过的变更类型直接卡死；业务规则调整要改代码 |
| B. 全 LLM | 灵活，能基于上下文泛化 | 输出不确定；可能忽略已沉淀规则、产生幻觉；无法单测 |
| C. 规则为主 + LLM 兜底 | 已知场景确定性高，未知场景不卡死 | 需同时维护规则表与模型调用，资源与时延开销更大 |

### 决定

选 **C**，边界如下：

| 环节 | 归属 | 说明 |
|---|---|---|
| 已知变更 → 场景 / 参数 / 阈值 | **规则** | 来自 `data/mapping.csv`，业务已确认 |
| 未知变更 → 场景推荐 | **LLM 兜底** | 模型只给候选，置信度低则回退全量（见 D3） |
| 结果解释 | **LLM** | 只做表达，不改结论（见 D6） |
| 是否放行 | **规则 + 人** | 模型不参与 |

### 理由

两类失败的代价不对称：漏测不可逆，多跑只是时间。规则能给出确定答案的地方交给模型，等于用不可逆的风险换一点灵活性。

而 LLM 的价值恰好只在"规则覆盖不到的地方"——那里本来就没有正确答案，模型的泛化才有意义。

### 后果

**好的**

- 已知场景的结论可回归、可单测覆盖
- 模型的不确定性被限制在"未知变更"这一个窄口子里
- 规则表本身就是一份可评审的业务知识库

**坏的**

- 规则表要持续维护，业务变化时要同步更新
- 未知变更首次出现会走 LLM 兜底，结果不如规则稳
- 同时维护两条路径，排查问题时要先判断走的是哪条

### 何时重新评估

- **未知变更占比 > 20%** → 规则表跟不上业务，应补规则，而不是扩模型
- **LLM 兜底准确率 > 95% 且可解释** → 可考虑扩大模型使用范围
- **LLM 兜底准确率长期 < 60%** → 撤掉模型兜底，改为直接人工

## D2 执行与判读分离

- **状态**：已采纳
- **日期**：2026-11-10
- **影响范围**：`agent/executor.py`、`agent/judge.py`

### 背景

编排要跑多步：查录制、压测、diff，每步产出不同结构的数据。
如果执行时顺手把「是否通过」也判了，平台调用和业务判定会长在同一段代码里。

### 决策驱动

- 平台是最容易变的部分（Mock / 真实 / 以后可能换供应商）
- 判读是最不该变的部分（业务判定标准）
- 判读逻辑要能脱离平台单测

### 候选方案

| 方案 | 优点 | 缺点 |
|---|---|---|
| A. 执行时顺手判 | 少一层数据契约，代码短 | 平台调用与业务判定耦合；换平台要重写判读 |
| B. 执行只返回数据，判读独立 | 判读可单测；换平台只改 `tools/` | 多一层契约，改返回结构要同步改两边 |
| C. 事件驱动（执行发事件，判读订阅） | 最解耦，可扩展多消费者 | 对当前规模是过度设计 |

### 决定

选 **B**。

### 理由

把「易变的」和「不该变的」隔开：平台会换，判定标准不该跟着换。
判读一旦独立，就能拿固定数据集回归——这也是 D6「结论必须可复现」的前提。

### 后果

**好的**

- 判读可以脱离平台做单测
- 换真实平台时，判读部分一行不用改

**坏的**

- 多一层数据契约：`executor` 改返回结构，`judge` 必须同步改
- 排查问题时要在两层之间跳一次

### 何时重新评估

- 判读开始依赖**执行过程状态**而非结果（比如「重试了几次才成功」）→ 这层分离会变别扭，应把执行元数据纳入契约
- 出现第三种消费者（比如看板）→ 那时 C 方案才划算

## D3 失败分级处置

- **状态**：已采纳
- **日期**：2026-11-10
- **影响范围**：`agent/executor.py` 的失败处理、`agent/judge.py` 的结论生成

### 背景

压测或 diff 任务失败时，有三种可能的处置：重做、跳过、交人。

- 一律重做 → 浪费时间，且重做后数据可比性下降（跨轮次环境已变）
- 一律跳过 → 等于取消门禁
- 一律交人 → 会产生**审批疲劳**：人一天审 20 次，开始不看就点通过，比直接跳过更危险

而失败本身不是同质的：有的能自己恢复，有的已经给出了明确答案，有的才是真的不知道。

### 决策驱动

- 漏测不可逆，时间可恢复
- 处置动作应由**失败类型**决定，而不是由「这次赶不赶时间」决定
- 任何处置都要留痕，能回答「这次为什么放行」

### 候选方案

| 方案 | 优点 | 缺点 |
|---|---|---|
| A. 统一重做 | 最保守 | 慢；重复失败概率高；跨轮次数据不可比 |
| B. 统一跳过 | 最快 | 等于取消门禁，漏测风险不可控 |
| C. 统一交人 | 灵活，人能看上下文 | 高频审批必然形式化，门禁名义存在、实际失效 |
| **D. 按失败类型分级** | 把人的注意力留给真正不确定的情况 | 分级规则需维护，分类错了会误判 |

### 决定

选 **D**，分三级：

| 失败类型 | 是否可判定 | 处置 |
|---|---|---|
| 录制未就绪、瞬时超时 | 可自愈 | 自动重试 ≤ 2 次；仍失败转人工 |
| diff 超阈值、性能不达标 | 可判定 | 直接判「不通过」，**不进人工** |
| 任务执行报错、结果缺失 | 不可判定 | 人工介入 |

### 理由

三类失败的**信息量不同**：

- 前两类已经给出了答案——要么能修好，要么已经明确不合格；
- 只有第三类是真的「不知道」，才需要人补判断。

把已经知道答案的事交给人，只会稀释人对真正未知问题的注意力。
**门禁的价值不是「每次都有人看」，是「每次异常都有人负责」。**

### 后果

**好的**

- 常规失败自动消化，人只处理真正不确定的情况
- 每一次放行都有明确的责任人和理由，可回溯
- 自愈过程留痕，能统计「哪类失败最常发生」

**坏的**

- 分级规则本身需要维护，新失败类型出现时要补分类
- 分类判错会导致该自愈的进了人工，或该人工的被自动放行
- 自动重试会延长单次验证时长（最坏情况 +2 轮）

### 何时重新评估

- **人工介入率 > 20%** → 说明分级太粗，需要细化失败类型
- **自愈后二次失败率 > 50%** → 说明重试策略无效，应改为直接判失败
- **出现一次「该人工却被自动放行」的事故** → 分级规则需要整体重审

## D4 Agent 不是门禁

- **状态**：已采纳
- **日期**：2026-11-10
- **影响范围**：整体架构（入口层）

### 背景

Agent 有两种触发方式：人主动发起（CLI / Chat），或系统强制触发（发布流程 webhook）。
选哪种，决定了这套东西**会不会被真的用起来**。

### 决策驱动

- 门禁的价值在「必须跑」，不在「好跑」
- 靠自觉触发的检查，迟早退化成「想起来才跑」
- 但纯强制入口又缺少人工探索的灵活性

### 候选方案

| 方案 | 优点 | 缺点 |
|---|---|---|
| A. 只做 Chat / CLI | 门槛低、灵活 | 依赖人的记忆，漏跑无感知 |
| B. 只做 webhook | 强制性强 | 无法应对「我想先试试」的探索场景 |
| C. 双入口，共用同一执行引擎 | 该强制的地方强制，该灵活的地方灵活 | 两个入口要维护 |

### 决定

选 **C**，但职责分开：

| 入口 | 定位 | 是否可绕过 |
|---|---|---|
| **Webhook** | 发布前强制卡点 | 不可 |
| **Chat / CLI** | 探索、临时验证 | 可以（但留痕） |

### 理由

Chat 降低门槛，但**解决不了「必须跑」**。把强制性和易用性拆到两个入口，各自解决一个问题，而不是让一个入口承担两种职责。

### 后果

**好的**

- 门禁的强制性由发布系统保证，不依赖 Agent 好不好用
- 探索场景不被流程卡住
- 执行逻辑只有一套，不会出现「chat 跑的和门禁跑的不一样」

**坏的**

- 两个入口都要维护，权限和审计要在入口层分别做
- 容易出现「chat 跑过了，但门禁还是重跑一遍」的重复

### 何时重新评估

- 发布系统已能强制调用 Agent → Chat 可只保留探索用途
- Chat 月使用量长期为 0 → 砍掉，只留 webhook + CLI

## D5 Mock 与真实实现同签名

- **状态**：已采纳
- **日期**：2026-11-10
- **影响范围**：`tools/`（全部）、`agent/main.py`（装配处）

### 背景

本地没有真实平台（R2 / ForceBot），或者有权限但环境不可用。
但编排逻辑本身（规划、执行、判读）需要先跑通、先能演示。

### 决策驱动

- 编排的价值在**决策**，不在接线
- 接线应该是可替换的，而不是重写的
- 演示不能依赖「刚好能连上平台」

### 候选方案

| 方案 | 优点 | 缺点 |
|---|---|---|
| A. 直接连真实平台开发 | 一次到位 | 依赖权限与环境；本地无法演示；单测跑不了 |
| B. Mock 先行，接口与真实一致 | 可离线开发、可单测、可演示 | Mock 可能偏离真实行为 |
| C. 录制回放（Record & Replay） | 最接近真实 | 需要先有一次真实运行；回放期数据会过期 |

### 决定

选 **B**，接口由 `tools/base.py` 的 `Tool.run(params) -> ToolResult` 统一定义，Mock 与真实实现同签名。

### 理由

只要签名稳定，**换真实实现只改一个 import**，编排逻辑一行不动。
这让「决策逻辑」和「平台能力」可以独立演进——前者是项目的价值，后者是迟早会有的东西。

### 后果

**好的**

- 本地可完整跑通三段式（规划 → 执行 → 判读），不依赖任何平台
- 可单测、可演示、可现场跑
- 真实接入时只替换 `main.py` 里的实例化

**坏的**

- Mock 可能过于理想（比如 rt 曲线太平滑、diff 总在阈值附近），掩盖真实环境的复杂度
- 上线前必须用真实数据回归一次，否则等于没验

### 何时重新评估

- Mock 与真平台行为偏差导致误判 → 引入 C（录制回放）做校准
- 真实平台已有稳定测试环境 → 可把 Mock 降级为「单测专用」，主流程走真实

## D6 判读只信规则，模型只做解释

- **状态**：已采纳
- **日期**：2026-11-10
- **影响范围**：`agent/judge.py`（结论生成）、`tools/llm.py`（解释文本）

### 背景

判读要输出「通过 / 不通过」。这件事有两种做法：让模型读完所有指标自行判断，或由阈值规则判定、模型只负责把结论讲成人话。

这个决定直接决定「结论能不能被复现」——而结论会被写进审批记录，影响放行。

### 决策驱动

- 结论错误不可逆（放行了不该放的），表达错误只是难听
- 同一个输入，任何人任何时间去跑，结论必须一样
- 出了事故要能回答「当时凭什么判通过」

### 候选方案

| 方案 | 优点 | 缺点 |
|---|---|---|
| A. 全 LLM 判读 | 能综合多指标、给出「像人」的判断 | 不可复现；可能编造理由；无法单测；出错时无法追溯依据 |
| B. 规则判读 + LLM 解释 | 结论确定；表达自然 | 解释可能与结论不符（说错话） |
| C. 纯规则 + 模板话术 | 完全确定 | 解释生硬，异常情况说不清 |

### 决定

选 **B**：结论由 `judge.py` 的阈值规则给出，模型只接收「已确定的结论 + 证据」，把它转成可读文本，**不允许修改结论字段**。

### 理由

两类错误的代价不对称：判错要命，说错只是难听。

另外，「可追溯」是门禁的前提——如果结论是模型生成的，那么审批人签的其实是模型的判断，责任链就断了。

### 后果

**好的**

- 结论永远可复现、可单测
- 模型无法改变放行结果，幻觉的影响被限制在文案层
- 审批记录里签的是规则，不是模型

**坏的**

- 模型可能把结论解释错（例如把 diff 超阈值说成性能问题）
- 需要模板兜底：模型输出异常时回退到固定话术

### 何时重新评估

- 出现「解释被误当成结论依据」的反馈
- 判读维度超过 10 个，规则组合开始爆炸
- 需要「多指标综合评分」而非单点阈值时（那时规则确实表达不了）

## D7 阈值从机制推导，不拍脑袋

- **状态**：已采纳
- **日期**：2026-11-10
- **影响范围**：`data/mapping.csv`（diff_threshold）、`agent/judge.py`（p99 容忍度）

### 背景

diff 阈值定 1%、p99 容忍定 10%——这类数字如果直接拍，会有两个后果：定松了漏问题，定紧了天天报警，最后大家把报警关掉。

更麻烦的是评审：每次有人质疑「凭什么是 1%」，都只能回答「经验」。

### 决策驱动

- 阈值必须能回答「为什么是这个数」，否则无法评审
- 阈值要能被证伪：什么样的数据说明它定错了

### 候选方案

| 方案 | 优点 | 缺点 |
|---|---|---|
| A. 拍经验值 | 快 | 不可辩护；人员变动后无人知其所以然 |
| B. 从历史数据统计（均值 + kσ） | 客观、可复算 | 需要足够历史样本；分布变化后失效 |
| C. 从机制推导（误差来源明确时） | 可解释、可预测 | 依赖对机制的准确理解；机制变了要重推 |

### 决定

优先 **C**，用 **B** 校准，**A** 只在无机制可推时兜底。

具体到本项目：

- **diff 阈值 1%**：同构迁移只换索引构建方式，语义不变，所以差异只应来自 ANN 近似。1% 对应 ef_search 在目标延迟下的近似误差水平；**超过 1%，说明差异不是近似，是逻辑问题。**
- **p99 容忍 10%**：来自业务可感知的延迟上限，超过即用户可感知。

### 理由

这两类阈值都有明确的误差来源，可以从机制反推，不该交给经验。
可推导的阈值有一个额外好处：**当机制变化时（比如换索引类型），你知道该重推哪一个数，而不是全部重新拍一遍。**

### 后果

**好的**

- 阈值可辩护，评审时不用吵
- 阈值偏了能定位原因（是机制变了，还是数据变了）

**坏的**

- 推导依赖对机制的准确理解，理解错了会得出很自信的错误阈值
- 机制变化（如 ANN 参数调整）后，阈值需要重推

### 何时重新评估

- **误报率 > 10%** → 阈值太紧，按 D7 的推导路径重新校准
- **出现一次漏放（应判未判）** → 阈值太松，立即重推
- **底层机制变化**（换索引类型、改 ef_search 默认值）→ 阈值必须重推

## D8 失败轮次的数据处理：保留，不覆盖

- **状态**：已采纳
- **日期**：2026-11-12
- **影响范围**：`store/repo.py`（attempt 表）、`skills/run.py`（execute）

### 背景

压测 / diff 执行可能失败或超时。失败后往往需要「重启再跑一轮」，
于是必须回答：**本轮的数据怎么办——覆盖上一轮，还是保留？**

这个决定直接影响两件事：失败原因还能不能查，以及历史趋势会不会被污染。

### 决策驱动

- 失败轮次本身是证据：它可能是环境问题，也可能是真实劣化
- 但失败轮次的指标**不可比**（跑了一半的值不能进趋势）
- 「重跑」和「新任务」在语义上不同，不能混成一个

### 候选方案

| 方案 | 优点 | 缺点 |
|---|---|---|
| A. 覆盖上一轮 | 表干净，查询简单 | 丢失失败现场，无法复盘「上次为什么挂」 |
| B. 直接丢弃失败轮 | 不污染趋势 | 同上，且丢掉失败频次这个信号 |
| C. 保留 + 隔离（attempt 链） | 可追溯、不污染、能算失败率 | 多一张表，查询时要过滤状态 |

### 决定

选 **C**：

- 每轮执行生成一条 `attempt`（`running` → `completed` / `aborted`）
- **失败轮只落 attempt，不写 task/report** —— 因此不会进入历史序列
- 重跑时 `parent_attempt` 指向上一轮，形成链
- 查询历史时默认只取 `completed`；诊断时可见 `aborted` 轮次

### 理由

失败数据和成功数据**性质不同**，混在一条序列里做趋势，等于把「跑到一半的值」当结论。

但丢弃又会丢失两类信息：失败原因的现场，以及失败发生的频率（后者本身就是质量信号）。

隔离而不是删除，是唯一同时保住两者的做法。

### 后果

**好的**

- 失败可追溯：`attempt` 里能看到第几轮、什么状态、失败原因
- 趋势不被污染：历史只统计 `completed`
- 可以回答「这套流程失败率多少」——这是以前没有的指标

**坏的**

- 多一张表和一层状态机，查询要记得过滤
- attempt 会持续增长，长期需要归档策略（见重估）

### 何时重新评估

- `attempt` 表行数 > 50 万 → 需要冷热分离或定期归档
- 出现「需要对比两次失败轮次」的需求 → 说明失败数据也要参与分析，规则要重定
- 重跑率长期 > 30% → 问题不在数据保留，在流程稳定性，应回到 D3 重新分级

## D9 失败必须有口径：阶段 + 类型

- **状态**：已采纳
- **日期**：2026-11-12
- **影响范围**：`agent/failure_taxonomy.py`、`store/repo.py`（attempt）、`skills/run.py`、`skills/diagnose.py`

### 背景

最初的版本只报「N 轮失败未计入」。这句话是空的——「2 轮失败」可能是沙箱没起来，
也可能是执行超时，还可能是报告没落库。三种情况的处置完全不同：
一个要找环境负责人，一个要重跑，一个要查存储。

**没有口径的失败率，是没法行动的。**

### 决策驱动

- 失败必须能直接指向处置动作，否则记录没有意义
- 不同阶段的失败，责任方不同（环境 / 数据 / 代码）
- 可重试性不同：有的重跑就好，有的重跑一百次也一样

### 候选方案

| 方案 | 优点 | 缺点 |
|---|---|---|
| A. 只记 status（成功/失败） | 简单 | 无法行动，等于没记 |
| B. 记自由文本 note | 灵活 | 不可聚合、不可统计 |
| C. 固定「阶段 × 类型」两级分类 | 可聚合、可统计、可定位 | 新类型要登记 |

### 决定

选 **C**，两级固定口径：

| 阶段 | 含义 | 典型类型 |
|---|---|---|
| `precheck` | 预检（不消耗资源） | 参数不合法 |
| `sandbox` | 环境准备 | 沙箱不可用 |
| `recording` | 录制就绪 | 录制未就绪 |
| `run` | 执行 | 执行超时 / 执行报错 |
| `report` | 报告生成 | 报告落库失败 |
| `judge` | 判读 | 判读异常 |

每个类型同时声明：**是否可自动重试**、**处置建议**。

界面与 API 一律输出「阶段 · 类型 + 次数」，禁止只给总数。

### 理由

失败的价值不在「有没有失败」，在「失败说明下一步该做什么」。

固定口径让三件事同时成立：可聚合（按类型统计）、可定位（责任方明确）、可自动化（可重试的自动重试，见 D3）。

### 后果

**好的**

- 「N 轮失败」变成「环境 1、超时 2、报告 1」，直接可行动
- 可以统计「哪一类失败最多」——这是流程改进的依据
- 与 D3 的分级处置对接：可重试的类型自动重试，不可重试的直接交人

**坏的**

- 新增失败类型时必须登记，否则会落到 unknown
- 分类边界需要判断（比如「录制未就绪」是环境还是数据问题），可能引起争论

### 何时重新评估

- `unknown` 类型占比 > 10% → 分类不全，需要补
- 同一类型连续失败 > 5 次 → 说明不是偶发，应升级为流程问题
- 出现「同一轮多个阶段失败」 → 需要定义主次（当前只记第一个）

## D10 一次执行 = 一个 job，内含独立成败的分支

- **状态**：已采纳
- **日期**：2026-11-12
- **影响范围**：`job` 表、`attempt.branch`、`skills/run.py`

### 背景

平台启动任务时会同时启动 diff 和压测，但这两条链路是**独立**的：
diff 的镜像打包或环境拉取失败，压测可能完全正常，最终照样产出压测报告。

如果用单一状态描述这次执行，diff 挂了就会把压测也标成失败。

### 决策驱动

- 报告要如实反映「哪部分有效、哪部分缺失」
- 失败必须能定位到分支，否则不知道该修哪条链路
- 部分成功是常态，不是异常

### 候选方案

| 方案 | 优点 | 缺点 |
|---|---|---|
| A. 单一状态（全成功/全失败） | 简单 | 无法表达部分成功；diff 失败会误伤压测 |
| B. job（聚合）+ 分支（明细） | 可表达 partial；失败归属清晰 | 多一层表结构 |
| C. 只记分支，不记 job | 最细 | 没有「这次执行整体如何」的视图 |

### 决定

选 **B**：

- **job**：一次执行请求，状态 `completed` / `partial` / `failed`
- **attempt**：每个分支（`diff` / `load`）一条，各自记录成败、阶段、失败类型

状态推导规则：全成功 → `completed`；部分成功 → `partial`；全失败 → `failed`。

**只有 `completed` 和 `partial` 才写 task/report**——全失败时连结论都没有。

### 理由

摘要需要聚合（job），处置需要定位（分支）。两个层次解决两个问题，缺一个都不行。

### 后果

**好的**

- `partial` 可以如实表达「diff 失败但压测有效」
- 失败能定位到具体分支，处置动作明确
- 可以分别统计「diff 失败率」和「压测失败率」

**坏的**

- 多一张表，状态要在两层之间保持一致
- 前端要展示两个层次的信息

### 何时重新评估

- 出现第三种分支（如全链路回放）→ 层级仍成立，但状态推导规则要重定义
- `partial` 占比 > 50% → 说明平台本身不稳定，问题不在记录方式

## D11 执行状态与结论有效性必须正交

- **状态**：已采纳
- **日期**：2026-11-12
- **影响范围**：`job.validity`、`store/repo.validity_from_aa`、卡片渲染

### 背景

任务「跑完了」不等于「结论可用」。

diff 的 AA 回放是零假设验证：同一版本跑两次，结果应该一致。如果 AA 的一致率本身就低，
说明环境或流量有问题——此时报告的 A/B 差异不可信。

这种情况任务**跑完了、报告也生成了**，但结论**不能用**。

### 决策驱动

- 「有没有产出」和「结论能不能用」是两个问题
- 混成一个状态，会让失败率统计失真
- 「无效」不是失败，处置方式完全不同：要查环境，不是重跑

### 候选方案

| 方案 | 优点 | 缺点 |
|---|---|---|
| A. 合并成一个状态（含 invalid） | 字段少 | 状态爆炸；无效和失败混算 |
| B. 两个正交字段 | 可组合、可分别统计 | 前端要展示两处 |
| C. 不做区分 | 省事 | 无效结论被当成有效用，风险最大 |

### 决定

选 **B**，两个字段：

| 字段 | 取值 | 描述 |
|---|---|---|
| `status` | `completed` / `partial` / `failed` | 执行层面 |
| `validity` | `valid` / `invalid` / `unknown` | 结论层面 |

**`validity` 的判据**：AA 观测一致率 `EMR_AA` 低于阈值（当前 90%）→ `invalid`；未提供 → `unknown`。

### 理由

一个描述过程，一个描述质量。组合起来四种情况都合法，且各自可统计：

- `completed + valid` → 正常
- `completed + invalid` → 跑完了但不可用
- `partial + valid` → 压测有效、diff 缺失（可接受）
- `failed + unknown` → 什么都没产出

### 后果

**好的**

- 可以分别统计「执行失败率」和「结论无效率」——这是两个不同的质量指标
- 无效结论不会被当成有效数据使用
- 与 D8 一致：无效轮次不进历史趋势

**坏的**

- 两个字段要一起维护，前端要展示两处
- `unknown` 容易被忽略（默认值太安全）

### 何时重新评估

- `invalid` 占比 > 20% → 测量系统本身有问题，先修环境再谈结论
- `unknown` 占比 > 50% → AA 校验没有接入，D11 形同虚设
- 引入压测的噪声基线后 → 压测也要有 `validity` 判据（当前压测无 AA，只有 diff 有）
