## D1 规则优先，模型兜底

- **状态**：已采纳
- **日期**：2026-11-10
- **影响范围**：`agent/planner.py`（场景选择）、`agent/judge.py`（结论解释）

### 背景

编排层要替人做三类判断：跑哪些场景、用哪档参数、结果怎么解释。这些判断过去由人凭经验做，现在要写进代码。

难点在于：业务里已经沉淀了大量**明确规则**（哪类变更影响哪些场景、阈值多少），但也有**没见过的新变更**。代码必须回答一个问题——规则和模型，谁说了算。

### 决策驱动

- 漏跑场景 → 漏测 → 不可逆；多跑场景 → 只是浪费时间
- 结论必须可回归：同样的输入，今天和一周后要得出同样的结果
- 规则是业务已经认可的事实，不能被模型"重新理解"一遍

### 候选方案

| 方案 | 优点 | 缺点 |
|---|---|---|
| A. 全规则 | 可预测、可单测、可回溯 | 遇到未见过的变更类型直接卡死；业务规则调整要改代码 |
| B. 全 LLM | 灵活，能基于上下文泛化 | 输出不确定；可能忽略已沉淀规则、产生幻觉；无法单测 |
| C. 规则为主 + LLM 兜底 | 已知场景确定性高，未知场景不卡死 | 需同时维护规则表与模型调用，资源与时延开销更大 |

### 决定

选 **C**，边界如下：

| 环节 | 归属 | 说明 |
|---|---|---|
| 已知变更 → 场景 / 参数 / 阈值 | **规则** | 来自 `data/mapping.csv`，业务已确认 |
| 未知变更 → 场景推荐 | **LLM 兜底** | 模型只给候选，置信度低则回退全量（见 D3） |
| 结果解释 | **LLM** | 只做表达，不改结论（见 D6） |
| 是否放行 | **规则 + 人** | 模型不参与 |

### 理由

两类失败的代价不对称：漏测不可逆，多跑只是时间。规则能给出确定答案的地方交给模型，等于用不可逆的风险换一点灵活性。

而 LLM 的价值恰好只在"规则覆盖不到的地方"——那里本来就没有正确答案，模型的泛化才有意义。

### 后果

**好的**

- 已知场景的结论可回归、可单测覆盖
- 模型的不确定性被限制在"未知变更"这一个窄口子里
- 规则表本身就是一份可评审的业务知识库

**坏的**

- 规则表要持续维护，业务变化时要同步更新
- 未知变更首次出现会走 LLM 兜底，结果不如规则稳
- 同时维护两条路径，排查问题时要先判断走的是哪条

### 何时重新评估

- **未知变更占比 > 20%** → 规则表跟不上业务，应补规则，而不是扩模型
- **LLM 兜底准确率 > 95% 且可解释** → 可考虑扩大模型使用范围
- **LLM 兜底准确率长期 < 60%** → 撤掉模型兜底，改为直接人工

## D2 执行与判读分离

- **状态**：已采纳
- **日期**：2026-11-10
- **影响范围**：`agent/executor.py`、`agent/judge.py`

**决定**：执行层只返回数据，不做任何判定；判读层只看数据，不碰执行。

**理由**：判读逻辑可以脱离平台单测——换真实平台时，判读部分一行不用改。

**后果**

- 好的：执行与判读可独立演进、独立测试
- 坏的：多一层数据契约，改了执行返回结构要同步改判读

**何时重新评估**：判读需要依赖执行过程的状态（而非结果）时，这层分离会变别扭

## D3 失败分级处置

- **状态**：已采纳
- **日期**：2026-11-10
- **影响范围**：`agent/executor.py` 的失败处理、`agent/judge.py` 的结论生成

### 背景

压测或 diff 任务失败时，有三种可能的处置：重做、跳过、交人。

- 一律重做 → 浪费时间，且重做后数据可比性下降（跨轮次环境已变）
- 一律跳过 → 等于取消门禁
- 一律交人 → 会产生**审批疲劳**：人一天审 20 次，开始不看就点通过，比直接跳过更危险

而失败本身不是同质的：有的能自己恢复，有的已经给出了明确答案，有的才是真的不知道。

### 决策驱动

- 漏测不可逆，时间可恢复
- 处置动作应由**失败类型**决定，而不是由「这次赶不赶时间」决定
- 任何处置都要留痕，能回答「这次为什么放行」

### 候选方案

| 方案 | 优点 | 缺点 |
|---|---|---|
| A. 统一重做 | 最保守 | 慢；重复失败概率高；跨轮次数据不可比 |
| B. 统一跳过 | 最快 | 等于取消门禁，漏测风险不可控 |
| C. 统一交人 | 灵活，人能看上下文 | 高频审批必然形式化，门禁名义存在、实际失效 |
| **D. 按失败类型分级** | 把人的注意力留给真正不确定的情况 | 分级规则需维护，分类错了会误判 |

### 决定

选 **D**，分三级：

| 失败类型 | 是否可判定 | 处置 |
|---|---|---|
| 录制未就绪、瞬时超时 | 可自愈 | 自动重试 ≤ 2 次；仍失败转人工 |
| diff 超阈值、性能不达标 | 可判定 | 直接判「不通过」，**不进人工** |
| 任务执行报错、结果缺失 | 不可判定 | 人工介入 |

### 理由

三类失败的**信息量不同**：

- 前两类已经给出了答案——要么能修好，要么已经明确不合格；
- 只有第三类是真的「不知道」，才需要人补判断。

把已经知道答案的事交给人，只会稀释人对真正未知问题的注意力。
**门禁的价值不是「每次都有人看」，是「每次异常都有人负责」。**

### 后果

**好的**

- 常规失败自动消化，人只处理真正不确定的情况
- 每一次放行都有明确的责任人和理由，可回溯
- 自愈过程留痕，能统计「哪类失败最常发生」

**坏的**

- 分级规则本身需要维护，新失败类型出现时要补分类
- 分类判错会导致该自愈的进了人工，或该人工的被自动放行
- 自动重试会延长单次验证时长（最坏情况 +2 轮）

### 何时重新评估

- **人工介入率 > 20%** → 说明分级太粗，需要细化失败类型
- **自愈后二次失败率 > 50%** → 说明重试策略无效，应改为直接判失败
- **出现一次「该人工却被自动放行」的事故** → 分级规则需要整体重审

## D4 Agent 不是门禁

- **状态**：已采纳
- **日期**：2026-11-10
- **影响范围**：整体架构

**决定**：Agent 只提供执行能力，门禁必须由发布流程强制触发（webhook），而不是靠人想起来调用 Agent。

**理由**：Chat 入口降低门槛，但**解决不了「必须跑」**。靠自觉触发的检查，迟早会退化成「想起来才跑」。

**后果**

- 好的：门禁的强制性由发布系统保证，不依赖 Agent 的易用性
- 坏的：需要同时维护 CLI/Chat 与 webhook 两个入口（但共用同一套执行引擎）

**何时重新评估**：当发布系统本身能强制调用 Agent 时，Chat 入口可以只保留「探索」用途

## D6 判读只信规则，模型只做解释

- **状态**：已采纳
- **日期**：2026-11-10
- **影响范围**：`agent/judge.py`（结论生成）、`tools/llm.py`（解释文本）

### 背景

判读要输出「通过 / 不通过」。这件事有两种做法：让模型读完所有指标自行判断，或由阈值规则判定、模型只负责把结论讲成人话。

这个决定直接决定「结论能不能被复现」——而结论会被写进审批记录，影响放行。

### 决策驱动

- 结论错误不可逆（放行了不该放的），表达错误只是难听
- 同一个输入，任何人任何时间去跑，结论必须一样
- 出了事故要能回答「当时凭什么判通过」

### 候选方案

| 方案 | 优点 | 缺点 |
|---|---|---|
| A. 全 LLM 判读 | 能综合多指标、给出「像人」的判断 | 不可复现；可能编造理由；无法单测；出错时无法追溯依据 |
| B. 规则判读 + LLM 解释 | 结论确定；表达自然 | 解释可能与结论不符（说错话） |
| C. 纯规则 + 模板话术 | 完全确定 | 解释生硬，异常情况说不清 |

### 决定

选 **B**：结论由 `judge.py` 的阈值规则给出，模型只接收「已确定的结论 + 证据」，把它转成可读文本，**不允许修改结论字段**。

### 理由

两类错误的代价不对称：判错要命，说错只是难听。

另外，「可追溯」是门禁的前提——如果结论是模型生成的，那么审批人签的其实是模型的判断，责任链就断了。

### 后果

**好的**

- 结论永远可复现、可单测
- 模型无法改变放行结果，幻觉的影响被限制在文案层
- 审批记录里签的是规则，不是模型

**坏的**

- 模型可能把结论解释错（例如把 diff 超阈值说成性能问题）
- 需要模板兜底：模型输出异常时回退到固定话术

### 何时重新评估

- 出现「解释被误当成结论依据」的反馈
- 判读维度超过 10 个，规则组合开始爆炸
- 需要「多指标综合评分」而非单点阈值时（那时规则确实表达不了）

## D7 阈值从机制推导，不拍脑袋

- **状态**：已采纳
- **日期**：2026-11-10
- **影响范围**：`data/mapping.csv`（diff_threshold）、`agent/judge.py`（p99 容忍度）

### 背景

diff 阈值定 1%、p99 容忍定 10%——这类数字如果直接拍，会有两个后果：定松了漏问题，定紧了天天报警，最后大家把报警关掉。

更麻烦的是评审：每次有人质疑「凭什么是 1%」，都只能回答「经验」。

### 决策驱动

- 阈值必须能回答「为什么是这个数」，否则无法评审
- 阈值要能被证伪：什么样的数据说明它定错了

### 候选方案

| 方案 | 优点 | 缺点 |
|---|---|---|
| A. 拍经验值 | 快 | 不可辩护；人员变动后无人知其所以然 |
| B. 从历史数据统计（均值 + kσ） | 客观、可复算 | 需要足够历史样本；分布变化后失效 |
| C. 从机制推导（误差来源明确时） | 可解释、可预测 | 依赖对机制的准确理解；机制变了要重推 |

### 决定

优先 **C**，用 **B** 校准，**A** 只在无机制可推时兜底。

具体到本项目：

- **diff 阈值 1%**：同构迁移只换索引构建方式，语义不变，所以差异只应来自 ANN 近似。1% 对应 ef_search 在目标延迟下的近似误差水平；**超过 1%，说明差异不是近似，是逻辑问题。**
- **p99 容忍 10%**：来自业务可感知的延迟上限，超过即用户可感知。

### 理由

这两类阈值都有明确的误差来源，可以从机制反推，不该交给经验。
可推导的阈值有一个额外好处：**当机制变化时（比如换索引类型），你知道该重推哪一个数，而不是全部重新拍一遍。**

### 后果

**好的**

- 阈值可辩护，评审时不用吵
- 阈值偏了能定位原因（是机制变了，还是数据变了）

**坏的**

- 推导依赖对机制的准确理解，理解错了会得出很自信的错误阈值
- 机制变化（如 ANN 参数调整）后，阈值需要重推

### 何时重新评估

- **误报率 > 10%** → 阈值太紧，按 D7 的推导路径重新校准
- **出现一次漏放（应判未判）** → 阈值太松，立即重推
- **底层机制变化**（换索引类型、改 ef_search 默认值）→ 阈值必须重推
