# algo_test_agent

算法质量平台的**编排 Agent** 原型：输入一个变更，输出一套可执行的验证计划，跑完给出「能不能上」的结论。

## 为什么做这个

平台能力（录制回放 / 压测 / diff）都在，但**每次变更跑什么、跑几档、阈值多少**仍然靠人脑判断。
这个项目要把「人的判断」变成可执行、可复现、可度量的编排逻辑。

## 设计原则

1. **规则优先，模型兜底**：能用配置表判断的，绝不用 LLM。
2. **接口隔离**：`tools/` 下每个工具都是抽象接口，Mock 与真实平台实现同一个签名，替换只改一个 import。
3. **执行与判读分离**：执行层只负责拿数据，判读层只看数据，两层可独立测试。
4. **不达标不放行**：Agent 只给「建议」，放行必须由规则 + 人共同决定。

## 分层

```
┌─ 触发层 ── webhook / CLI
├─ 理解层 ── 变更 → 影响面
├─ 规划层 ── 影响面 → 执行计划（场景 / 档位 / 阈值 / 顺序）
├─ 执行层 ── 录制就绪 → 压测 → diff → 报告
└─ 判读层 ── 结果 → 结论 + 归因 + 建议
```

## 目录

```
agent/            编排核心：规划 / 执行 / 判读
  ├─ main.py      入口（CLI demo）
  ├─ planner.py   变更 → 执行计划
  ├─ executor.py  按 DAG 执行，带重试
  ├─ judge.py     结果 → 结论与卡片
  └─ models.py    数据结构
tools/            工具层（抽象接口 + Mock 实现）
  ├─ base.py      Tool 抽象
  ├─ r2_mock.py   录制回放（状态机）
  ├─ forcebot_mock.py 压测（可复现拐点）
  ├─ diff_mock.py diff（可复现 97% 场景）
  └─ llm.py       LLM 薄封装（仅两处使用）
data/             场景台账 / 变更映射 / 历史案例
docs/             架构说明与设计决策
tests/            三个必跑 case
```

## 快速开始

```bash
python3 agent/main.py --change "图A 召回算子改动" --scenario pass
python3 agent/main.py --change "图A 召回算子改动" --scenario diff_fail
python3 agent/main.py --change "图A 召回算子改动" --scenario recording_broken
```

## 三个阶段

| 阶段 | 内容 | 是否需要 LLM |
|---|---|---|
| P1 | 规则编排 + 执行 + 判读 | 否 |
| P2 | 反思重试（录制未就绪自动重启） | 否 |
| P3 | 未知变更场景推荐 + 自然语言归因 | 是 |

当前仓库完成 P1，P2 的骨架已留出。

## 边界

- 不是门禁：门禁必须由发布流程强制触发，Agent 只提供执行能力。
- 不放行：判读结果只作为建议，最终放行由人签字。
